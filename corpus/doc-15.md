# Стратегії паралельного виконання та ізоляція субагентів

Паралелізація роботи агентів здатна суттєво скоротити загальний час виконання (wall clock time), проте створює ризики конфліктів стану та помножує споживання токенів.

## 1. Паралельне читання проти послідовного запису
- Безпечна паралелізація (Fan-out): операції лише для читання (дослідження коду, аудит специфікації, перевірка інваріантів) запускаються паралельно через пул фіксованої ширини (concurrency limit = 2..4).
- Суворо послідовний запис: агенти, що модифікують файлову систему або код, повинні діяти в ізольованих просторах.

## 2. Ізоляція через git worktree
Якщо декілька задач або субагентів повинні вносити зміни, кожен з них отримує окреме робоче дерево `git worktree` на унікальній гілці. Це запобігає перезапису однакових файлів та гонці процесів лінтера й компілятора.

## 3. Обмеження пулу конкурентності (Concurrency Pool)
Необмежений запуск десятків агентів одночасно (`Promise.all` без лімітів) призводить до вичерпання rate-limits провайдерів та черг локальних моделей. Фіксована черга з шириною 2–4 є оптимальною для стабільності середовища.
